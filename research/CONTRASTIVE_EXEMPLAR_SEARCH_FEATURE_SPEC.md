# Contrastive Exemplar Search — Archives App Implementation Specification

Last updated: 2026-09-15
Status: Proposed implementation specification
Target branch: `feature/embed-search`

## 1. Purpose

Implement an opt-in search workflow that ranks archive files using one to three positive examples and, optionally, one to three negative examples. Positive examples describe the kind of record the archivist wants; negative examples describe nearby material that should rank lower.

The feature is an extension of the existing archive-search product. It must preserve the current lexical search behavior, file-hash result identity, archive-scope semantics, authorization behavior, file-information navigation, and non-destructive operating model.

The feature is not a filing recommendation engine. It supplies an explainable ranking signal for human review.

### 2.1 Existing app capabilities to reuse

The app already provides:

- `archives_application/archiver/archive_search.py` with `ArchiveSearchRequest`, `ArchiveSearchRun`, scope resolution, file-hash-level result grouping, metadata/location enrichment, and archive-search telemetry.
- `GET/POST /archives_search` as the canonical HTML lexical search workflow; `/file_search` remains a compatibility alias.
- `POST /api/archives_search` for the existing lexical/content search API.
- `GET /api/file_info` and `GET /api/project_info` with session or HTTP Basic authentication through `FlaskAppUtils.authenticate_active_api_user()`.
- Scope compilation for all archives, location prefixes, projects, and CAANs through `projects.file_server_location` and `project_caans`.
- User-facing path conversion through `FileServerUtils.user_path_from_db_data()`.
- `file_contents.minilm_emb` mapped as `Vector(384)` and an existing IVFFlat cosine index.
- `archive_search_runs` for lexical-search telemetry, but its current constraints describe only the four lexical modes (`combined`, `filename_only`, `filepath`, `content`).

### 2.2 Existing database/search facts

The canonical archive data model is:

```text
files.hash             canonical result identity
file_locations         one or more display/access locations
file_contents          extracted text and file-level MiniLM embedding
projects/CAAN tables   scope metadata
```

The reference describes PostgreSQL 17.10 with pgvector 0.8.1, approximately 763K unique files, approximately 1M locations, and approximately 513K files with MiniLM embeddings at its 2026-09-02 snapshot. Counts change as the scraper runs and must be re-profiled before rollout.

`file_contents.minilm_emb` is a 384-dimensional vector generated by the scraper's `all-MiniLM-L6-v2` embedder. The app model currently records `minilm_model`, but the feature must verify the actual production values rather than assume casing or a single historical default.

### 2.3 Important implementation gaps

1. The app's `pyproject.toml` does not currently declare `sentence-transformers`, `torch`, or an embedding provider. The scraper owns `embedding/minilm.py` and generates the stored vectors.
2. There is no safe app-side text-to-embedding service contract yet. A Flask request must not load a transformer model ad hoc, download model weights, or silently use a different model.
3. The current repository does not contain a `tests/` directory. The implementation must establish a focused test layout rather than assuming one exists.
4. `archive_search_runs` is shaped for lexical requests and should not be expanded casually to store exemplar-specific state. Feature telemetry needs a reviewed migration or a separate table.
5. Existing archive-search API authentication accepts a legacy JSON-body credential path. New contrastive endpoints should use the shared session/HTTP Basic policy used by the newer read-only APIs.

## 3. Product boundary

### 3.1 V1 goals

V1 must allow an authenticated user to:

- Select one to three accessible indexed files under **Like these**.
- Select zero to three accessible indexed files under **Unlike / ignore these**.
- Run a contrastive search within all archives, a location prefix, a project, or a CAAN.
- See one result per canonical file hash, with a preferred in-scope location.
- See contrastive and ordinary positive-prototype similarity for every result.
- Understand, in concise plain language, why a result was promoted or lowered.
- Exclude selected exemplar hashes from the result set.
- Open the normal file-information page and use existing path/location workflows.
- Submit lightweight usefulness feedback after reviewing the result set.
- Retain ordinary archive search as an explicit fallback and unchanged default.

### 3.2 V1 non-goals

V1 must not:

- Move, rename, file, relabel, delete, or otherwise mutate archive records.
- Replace `/archives_search` or change its default ranking.
- Infer a filing code or automatically classify a document.
- Upload a new file solely as an exemplar.
- Persist uploaded material.
- Compare vectors from different embedding models.
- Perform chunk-level vector retrieval.
- Use an LLM, RAG, generated summary, or generated document claim.
- Treat scores as probabilities or filing correctness.
- Expose folder-background residualization as a normal user-facing control before evaluation.
- Store raw pasted text or exemplar identities in telemetry by default.

## 4. Pre-implementation work and go/no-go gates

The feature should not be implemented until the following work is complete or explicitly accepted as a staged limitation.

### 4.1 Database and embedding preflight

Run read-only checks against a production-like database and record the results in the implementation issue or deployment notes:

1. Confirm the `vector` extension and pgvector version.
2. Confirm `file_contents.minilm_emb` has dimension 384 for every non-null vector.
3. Group non-null embeddings by `minilm_model`, including null/blank values and casing variants.
4. Verify that all model groups selected for search are the same semantic model and dimension. Do not combine incompatible model labels merely because they are both 384-dimensional.
5. Measure embedding coverage by extension and by representative all-archive, top-level, project, and CAAN scopes.
6. Measure the number of candidate files with null embeddings, extraction failures, thin text, and multiple locations.
7. Confirm the IVFFlat index exists, is valid, uses cosine operators, and has an appropriate list count for the current corpus.
8. Run `EXPLAIN (ANALYZE, BUFFERS)` for representative scoped and unscoped KNN queries, including the proposed scope CTE and exemplar-hash exclusion.
9. Confirm the application database role can `SELECT` the required tables and telemetry role/migration privileges are available through the normal deployment process.
10. Verify that the selected scope can be compiled without filesystem access and that all path-boundary predicates match existing archive-search semantics.

The implementation must record the measured embedding model identifier and current coverage in deployment documentation; it must not hard-code the reference document's historical row counts as acceptance thresholds.

### 4.2 Text-exemplar decision gate

The overview permits optional pasted positive or negative text only when the application can generate a compatible MiniLM vector. The current app cannot do that safely. Before enabling text examples, choose one of these approaches:

**Recommended approach:** introduce a shared embedding-provider contract owned by the scraper/platform layer. It must expose the exact model identifier, dimension, normalization behavior, model artifact/version, and a bounded batch text-encoding operation. The web app should call a controlled internal service or use a separately provisioned worker process, not import and initialize `SentenceTransformer` in every Flask worker.

**Acceptable staged approach:** ship file-exemplar-only V1 with `CONTRASTIVE_SEARCH_TEXT_EXAMPLES_ENABLED=false`; retain the request/schema fields but return a clear validation error when text is supplied. Enable text only after provider and latency/security testing.

**Not acceptable:** adding an unpinned model dependency to the Flask app, downloading weights during a request, using a different model for text than for stored files, or silently returning a lexical-only result.

When text examples are enabled, verify that the provider produces L2-normalized 384-dimensional vectors for `all-MiniLM-L6-v2` and that its normalization matches stored scraper output. A provider contract test must compare known fixture texts against reference vectors within a documented tolerance.

### 4.3 Telemetry/schema decision gate

Review the existing `archive_search_runs` retention and privacy intent. The recommended design is a new `contrastive_search_runs` table because the existing table has lexical-mode checks, a required `query_text`, and no exemplar fields.

The database migration must be authored and applied in the database repository through Alembic, using the approved schema owner. Do not create DDL directly from the Flask app or add a migration only to this repository.

If product owners instead approve extending `archive_search_runs`, update its check constraints, nullability, indexes, ORM mapping, API contract, and retention policy as one reviewed change. Do not add a `contrastive` mode to the current check constraint without the corresponding fields and migration.

### 4.4 Test and local-environment gate

Before coding:

- Create a `tests/` layout with an app-independent vector-math/payload test layer.
- Add a test configuration that does not require production credentials, a live SMB mount, or a real Google credential file.
- Define fixtures for vector rows, duplicate locations, scopes, missing embeddings, mixed model labels, and selected-exemplar exclusion.
- Confirm `uv sync` can reproduce the app environment on Ubuntu/WSL.
- Confirm a configured PostgreSQL/pgvector test database or a documented integration-test environment for query-plan and KNN tests.
- Decide whether embedding-provider tests run in CI, in a scraper environment, or only as an explicitly documented operational smoke test.
- If vector math imports NumPy directly, declare NumPy as a direct app dependency rather than relying on Pandas' transitive dependency.

### 4.5 Performance and rollout gate

Set measured defaults only after benchmarking:

- result limit;
- candidate-pool multiplier and cap;
- IVFFlat probes;
- statement timeout;
- maximum positive/negative example counts;
- optional text length limits;
- maximum all-archive concurrency.

If all-archive searches cannot meet the interactive budget, retain them with a warning, require a scope for contrastive search, or route them to an asynchronous job. Do not conceal a timeout behind a generic empty-results page.

### 4.6 Go/no-go checklist

Implementation may begin when:

- the model/dimension policy is confirmed;
- embedding coverage and KNN plans are measured;
- text-exemplar support is either provisioned or explicitly disabled;
- telemetry schema ownership and migration sequencing are approved;
- authentication and record-visibility behavior are confirmed;
- a test database or equivalent query benchmark is available;
- branch work is isolated to `feature/embed-search`.

## 5. Proposed architecture

### 5.1 New service module

Add `archives_application/archiver/contrastive_search.py` as a transport-neutral service. Keep route functions thin.

The service should own:

1. strict request normalization and validation;
2. exemplar lookup and model compatibility validation;
3. optional text embedding-provider calls;
4. vector normalization and prototype construction;
5. scope resolution by reusing the existing archive-search scope compiler;
6. candidate KNN retrieval and application/SQL re-ranking;
7. file-hash exclusion and result deduplication;
8. metadata, location, and file-information URL enrichment;
9. explanation-code generation;
10. run telemetry lifecycle and feedback serialization.

Reuse small, stable helpers from `archive_search.py` where practical, especially `resolve_scope`, `_fetch_locations`, `_select_primary_location`, and archive path conversion. Avoid importing private helpers blindly if their contracts are not stable; move shared behavior to a clearly named module if needed.

### 5.2 Routes

Add a beta HTML workflow:

```text
GET  /contrastive_search
POST /contrastive_search
```

Add an authenticated JSON endpoint:

```text
POST /api/contrastive_search
```

Use `FlaskAppUtils.authenticate_active_api_user()` for the JSON endpoint. Do not introduce credentials in the JSON body for this new API. HTTP Basic requests must be protected by HTTPS in deployment.

Add a feedback endpoint only if the product wants feedback from non-browser clients:

```text
POST /api/contrastive_search/<run_id>/feedback
```

The HTML workflow may submit feedback through the same endpoint or a standard form action. Feedback must be scoped to the authenticated user and run ownership/visibility policy.

Do not change the default `/archives_search` route, its existing modes, or its existing API response. Add a navigation link or an optional clearly labelled entry point after the beta is ready.

### 5.3 Optional exemplar-picker support

The file picker must search or browse only through existing archive access rules. It should return canonical file hash, filename, primary user-facing location, project/path context, and embedding availability.

The initial picker may reuse the existing archive-search query and file-information service for lexical lookup. If a dedicated endpoint is needed, define it separately and keep it read-only:

```text
GET /api/contrastive_exemplars?query_text=...&scope_type=...&scope_value=...&limit=...
```

A picker result must not be selectable unless its canonical file has a compatible non-null embedding. The UI should distinguish “indexed but not embedding-searchable” from “not found.” Do not reveal inaccessible records merely because their hash was supplied.

## 6. Request contract

### 6.1 HTML form fields

The HTML form should contain:

- `positive_file_hashes`: one to three selected file hashes, represented by controlled picker selections rather than free-form hidden values alone.
- `negative_file_hashes`: zero to three selected file hashes.
- `positive_text`: optional short text, shown only when text examples are enabled.
- `negative_text`: optional short text, shown only when text examples are enabled.
- `scope_type`: `all`, `location`, `project`, or `caan`.
- `scope_value`: the value for the selected scope.
- `extensions`: optional comma-separated extension filter.
- `limit`: optional bounded result limit if exposed; otherwise use the configured HTML limit.
- `show_baseline`: boolean, default true.

The form must reject a submission with no positive file and no enabled positive text. Negative examples are optional.

### 6.2 JSON request

The JSON endpoint accepts exactly these fields:

```json
{
  "positive_file_hashes": ["hash-a", "hash-b"],
  "negative_file_hashes": ["hash-c"],
  "positive_text": null,
  "negative_text": null,
  "scope_type": "project",
  "scope_value": "4932",
  "extensions": "pdf,docx",
  "limit": 50,
  "show_baseline": true
}
```

Rules:

- Request body must be a JSON object.
- Unknown fields are rejected with `400`.
- Positive hashes are required unless enabled positive text is non-empty.
- Positive and negative hash lists must be arrays of strings, with no duplicates within either list.
- A hash may not appear in both lists.
- Positive file hashes: maximum three.
- Negative file hashes: maximum three.
- Hashes are looked up by `files.hash`; the request must not accept arbitrary vector values.
- Every selected file must have a non-null embedding with the approved model and dimension.
- `scope_type` and scope behavior must match `ArchiveSearchRequest`/`resolve_scope`.
- Scope inputs are mutually exclusive and directory matching is boundary-safe.
- Extension filters use the existing normalized extension syntax.
- `limit` is an integer between one and the configured maximum; booleans are not accepted as integers.
- `show_baseline` accepts a JSON boolean only.
- Pasted text is rejected while the text feature flag is disabled. When enabled, enforce a documented maximum length, trim outer whitespace, reject empty values, and never store raw text in telemetry.
- Negative text is invalid when it is the only negative input and text embedding is disabled.

### 6.3 HTTP responses

`POST /api/contrastive_search` returns:

- `200` for a successful search, including zero results;
- `400` for malformed or semantically invalid input;
- `401` for missing/invalid active-user authentication;
- `404` only when a requested scope selector has the same not-found semantics as existing archive search; selected exemplar hashes should not produce a record-existence oracle;
- `409` for an explicitly detected ambiguous scope/selector if the existing scope contract requires it;
- `413` for a configured text/input-size violation if that status is adopted consistently;
- `422` may be used for a validly shaped request whose examples cannot be used, but prefer `400` unless the API standards establish `422`;
- `500` for unexpected errors after logging a correlation/run identifier;
- `503` for a controlled provider/DB timeout if the deployment distinguishes temporary capacity failure from malformed input.

## 7. Exemplar eligibility and permission rules

### 7.1 File examples

For each selected hash:

1. Load the canonical `files` row and `file_contents` row.
2. Require `minilm_emb IS NOT NULL`.
3. Require the approved `minilm_model` value and `vector_dims(minilm_emb) = 384`.
4. Confirm the user may see the file through existing archive access behavior.
5. Resolve at least one display location. A canonical hash without a location may be rejected for a user-facing exemplar because the picker cannot explain what was selected.
6. Do not require the exemplar to be inside the candidate scope unless product owners explicitly choose that restriction. The default recommendation is to allow an accessible exemplar from any scope while making the candidate scope conspicuous.

If record-level location permissions are introduced later, visibility must be evaluated before returning exemplar metadata or results. A hash must never reveal inaccessible locations or the existence of a protected record.

### 7.2 Duplicate and overlap rules

- Re-selecting a file in the same group is rejected or idempotently ignored by the UI; the API rejects duplicate hashes.
- Positive/negative overlap is a `400` validation error.
- Candidate rows whose hash equals any selected exemplar hash are excluded before ranking and remain excluded after any re-ranking.
- If two selected locations resolve to the same hash, the hash contributes once with equal exemplar weight; location count must not increase vector weight.

## 8. Ranking and scoring specification

### 8.1 Vector preparation

All input vectors must be treated as model outputs, not as trusted normalized values. Normalize every exemplar vector before aggregation:

```text
normalize(v) = v / ||v||
```

Reject zero-length or non-finite vectors. The provider must return finite values; database vectors should be checked defensively.

For positive vectors `P`:

```text
positive_prototype = normalize(mean(normalize(p) for p in P))
```

For negative vectors `N`, when present:

```text
negative_prototype = normalize(mean(normalize(n) for n in N))
```

The initial negative-example strength is an application-controlled configuration value, not a user control:

```text
beta = 0.25
```

The exact default must be confirmed through evaluation and stored with each run. If no negative examples are present, the negative term is omitted.

The contrastive query is:

```text
query = normalize(positive_prototype - beta * negative_prototype)
```

If the combined vector norm is below a configured epsilon, return a validation response explaining that the selected positive and negative examples are too similar or contradictory. Do not fall back silently to a different query.

### 8.2 Ordinary baseline

The ordinary baseline is positive-prototype similarity:

```text
ordinary_similarity(candidate) = cosine(candidate, positive_prototype)
```

The refined score is:

```text
contrastive_similarity(candidate) = cosine(candidate, query)
```

For diagnostics and explanations, also calculate when available:

```text
positive_similarity(candidate) = cosine(candidate, positive_prototype)
negative_similarity(candidate) = cosine(candidate, negative_prototype)
```

Do not present these values as probabilities. They are relative ranking signals and may be negative or close together.

### 8.3 Candidate retrieval

Use one file-level KNN query over `file_contents.minilm_emb`, constrained by a file-hash scope CTE. The query must:

- compile selected scope prefixes using the existing boundary-safe predicate;
- select distinct file hashes before joining display locations;
- require a non-null approved-model embedding;
- apply extension filters before final limiting where practical;
- exclude all selected exemplar hashes;
- order by vector distance to the contrastive query;
- retrieve a bounded candidate pool larger than the displayed limit;
- avoid joining every `file_locations` row before KNN limiting.

Conceptual SQL shape:

```sql
WITH scoped_file_hashes AS (
    SELECT DISTINCT f.hash AS file_hash
    FROM file_locations fl
    JOIN files f ON f.id = fl.file_id
    WHERE <existing archive-search scope predicate>
),
knn_candidates AS (
    SELECT
        fc.file_hash,
        1 - (fc.minilm_emb <=> CAST(:contrastive_query AS vector)) AS contrastive_similarity,
        1 - (fc.minilm_emb <=> CAST(:positive_prototype AS vector)) AS ordinary_similarity,
        1 - (fc.minilm_emb <=> CAST(:negative_prototype AS vector)) AS negative_similarity
    FROM file_contents fc
    JOIN scoped_file_hashes sfh ON sfh.file_hash = fc.file_hash
    WHERE fc.minilm_emb IS NOT NULL
      AND fc.minilm_model = :embedding_model
      AND fc.file_hash NOT IN (...selected hashes...)
      AND <extension predicate>
    ORDER BY fc.minilm_emb <=> CAST(:contrastive_query AS vector)
    LIMIT :candidate_pool_limit
)
SELECT *
FROM knn_candidates
ORDER BY contrastive_similarity DESC, ordinary_similarity DESC, file_hash ASC
LIMIT :result_limit;
```

Use SQLAlchemy `text()`/bound parameters or an equivalent safe query builder. Never interpolate hashes, scope prefixes, vectors, extensions, or limits into SQL text.

The actual query must be benchmarked with the production pgvector version. If scope filtering prevents a good indexed KNN plan, retrieve a bounded indexed pool and apply scope-aware filtering/re-ranking in a controlled way; do not scan every vector for every request.

### 8.4 Candidate pool and deterministic ordering

Start with configurable values such as:

```text
candidate_pool_limit = max(result_limit * 20, 500)
candidate_pool_hard_cap = 5000
```

These are starting hypotheses, not final values. Measure recall and latency against an exact or generously pooled baseline. Ties must be deterministic using, in order:

1. contrastive similarity descending;
2. ordinary similarity descending;
3. positive similarity descending;
4. file hash ascending.

A selected exemplar must remain absent even if it would otherwise rank in the candidate pool.

### 8.5 Optional folder-context discounting

Do not expose this in default V1. Keep it behind a feature flag and an evaluation-only configuration.

When enabled for a scope with enough embedded files:

```text
background = normalize(mean(scope embeddings excluding selected exemplars))
residual(e, b) = normalize(e - dot(e, b) * b)
score = cosine(residual(query, background), residual(candidate, background))
```

Residualize both query and candidate. Do not residualize only the query. Disable when the scope has fewer than a configured minimum sample or when the background/query/candidate residual becomes near-zero. Record whether it was enabled in telemetry.

## 9. Result contract and explanations

### 9.1 Result fields

Each HTML/API result should include:

- `result_rank`;
- `file_hash`;
- `filename`;
- `extension`;
- `size_bytes` and display size;
- primary user-facing location, preferring an in-scope location;
- additional location count;
- `contrastive_similarity`;
- `ordinary_similarity`;
- `positive_similarity`;
- `negative_similarity` or null;
- optional rank delta versus ordinary baseline;
- an explanation code and rendered explanation;
- normal file-information URL/action.

A result is one canonical file hash. Full location lists remain available through the existing file-information page or an explicit details control; do not duplicate every location as a result row.

### 9.2 Explanation rules

Explanations must be generated from numeric relationships and controlled labels, not from an LLM. Suggested deterministic rules:

- `positive_match`: positive similarity exceeds the configured positive threshold or the result ranks in the top positive-prototype set.
- `negative_penalty`: negative similarity exceeds the configured negative threshold and the refined score is lower than ordinary similarity by the configured margin.
- `contrastive_promotion`: refined rank is materially better than ordinary rank.
- `ordinary_context_match`: ordinary similarity is high but refined rank is materially worse.
- `no_negative_set`: no negative examples were supplied; refined ranking is positive-example similarity.
- `low_margin`: refined and ordinary scores are too close to support a strong explanation.

Render examples such as:

- “Matches the commissioning and functional-testing examples.”
- “Ranked lower because it resembles the correspondence examples.”
- “Similar under ordinary search, but ranked lower after the unlike examples were applied.”
- “No unlike examples were supplied; this is positive-example similarity.”

Do not claim that the result is correct, belongs to a filing code, or was lowered for a semantic concept not represented by the selected examples.

### 9.3 Baseline comparison

The result page must make the comparison explicit:

- default result ordering is contrastive;
- a toggle/tab/sort control shows ordinary positive-prototype ordering;
- both views use the same scope, candidate eligibility, exemplar exclusion, and result limit;
- changing the display ordering must not trigger a second full database search when both score sets are already present;
- the UI labels scores as similarity signals, not percentages.

## 10. HTML UX specification

### 10.1 Entry point and labels

The primary entry point should be labelled **Find related records**. Avoid “vector,” “subtraction,” “residualization,” and “embedding arithmetic” in user-facing copy.

The page should explain:

> Choose records you want more like and, optionally, records you want ranked lower. Results are suggestions for review, not filing decisions.

### 10.2 Like-these control

- Label: **Like these**.
- Helper: “These examples define the kind of record you want to find.”
- Add button opens a search/browse picker using current archive access behavior.
- Each selected item is a removable chip containing a short filename plus enough path/project context to disambiguate it.
- Show an embedding-availability state while selecting; do not allow a non-embedded file to be submitted as an exemplar.
- Prevent duplicate selection.
- Display `1–3 selected` and enforce the maximum on both browser and server.

### 10.3 Unlike control

- Label: **Unlike / ignore these**.
- Helper: “These examples may be related, but should rank lower.”
- Explain that they are not deleted, excluded from the archive, or removed from document text.
- Optional and capped at three.
- Show a gentle warning when the selected negative examples have very low mutual similarity or belong to visibly unrelated contexts. The server remains authoritative; this warning must not prevent submission unless the query vector is invalid.

### 10.4 Text examples

When disabled, do not render active text controls or render them as an explicitly marked future capability. When enabled, show separate short fields:

- **Also like this description**.
- **Also avoid this description**.

Display the model/availability limitation in help text, not an implementation detail. Enforce length and do not retain typed text after the request unless a separately approved saved-search feature exists.

### 10.5 Scope and filters

Reuse the existing all/location/project/CAAN scope choices and field validation. The selected scope must be prominent in the result header. Scope compilation and warning messages should match `/archives_search`.

Optional extension filtering should reuse existing normalization and bounds. Do not add filing-code or document-type filters unless they already have a reliable, authorized data contract.

### 10.6 Results page

Show:

- selected scope;
- counts of positive/negative examples;
- whether text examples were used;
- contrastive/ordinary view control;
- result count and limit warning;
- filename and normal file-information link;
- preferred archive path;
- project/filing-code context when available, clearly labelled as metadata context;
- contrastive and ordinary similarity signals;
- concise explanation;
- a details control for numeric diagnostics and additional locations;
- **Was this useful?** feedback control.

Do not render a raw vector or expose internal model operations to normal users.

## 12. Telemetry and persistence

### 12.1 Recommended database table

Add a migration in the database repository for `contrastive_search_runs`:

```text
id                         bigint primary key
search_timestamp           timestamptz not null default now()
duration_ms                bigint nullable
user_id                    integer nullable references users(id) on delete set null
requested_scope_type       varchar(20) not null
requested_scope_value      text nullable
```

Add timestamp, user/timestamp, status/timestamp, and request-source indexes consistent with `archive_search_runs`.

Default telemetry must not store raw pasted text or selected exemplar hashes. If evaluation requires exemplar identity, obtain explicit policy approval and use access-controlled, retention-limited fields; do not put hashes in general-purpose logs.

### 12.2 Run lifecycle

Follow the established `ArchiveSearchRun` pattern:

1. Validate the request before creating a run.
2. Insert and commit an `incomplete` run before KNN execution.
3. Measure monotonic request duration.
4. Finalize as `successful` with result count and coverage.
5. Finalize as `failed` with duration on execution error.
6. Preserve `incomplete` if the process terminates before finalization.
7. Telemetry failure must not replace a successful search response.

The ORM model belongs in `archives_application/models.py` only after the database migration exists and the live schema is verified. The app model must match nullable/default/check/index behavior exactly.

### 12.3 Feedback

If feedback is enabled, store a minimal row or fields:

- run ID;
- authenticated user ID where policy permits;
- usefulness rating, for example `useful`, `mixed`, `not_useful`;
- optional controlled reason (`too_generic`, `negative_examples_helped`, `negative_examples_hurt`, `scope_wrong`, `no_good_match`, `other` only if free text is approved);
- timestamp.

Do not infer usefulness solely from opening a result. Result opens and path-copy actions may be separate aggregate telemetry if existing policy permits.

## 13. Security, privacy, and failure behavior

- Require an authenticated active user for the HTML workflow if current archive search requires it; otherwise match the existing archive-search access policy explicitly. Do not accidentally make selected exemplars or locations public.
- Use shared API authentication for the JSON endpoint.
- Apply existing CSRF protection to the HTML form; use the established API policy for JSON.
- Validate hashes as identifiers, never as SQL fragments or filesystem paths.
- Use existing path conversion helpers; do not perform SMB/file-server access during vector retrieval.
- HTML-escape filenames, paths, project names, and metadata. Only controlled explanation markup may be rendered as safe, and preferably explanations should be plain text.
- Avoid logging raw input text, passwords, vectors, or full selected-file metadata at normal log level.
- Return a generic “selected example cannot be used” error rather than distinguishing missing hash, inaccessible hash, or missing embedding when that distinction would create an existence oracle.
- If the query vector collapses to near zero, return a clear validation message and preserve the search form selections.
- If no candidates have approved embeddings in scope, return zero results plus coverage/warning information; do not claim that no substantively related records exist.
- If the database statement times out, report a controlled timeout warning/status and suggest narrowing scope; do not present an empty successful result.
- Provider failure must identify that text examples are temporarily unavailable without exposing internal model paths or credentials.

## 14. Performance and operational requirements

### 14.1 Query behavior

- Keep the vector search file-hash-level.
- Resolve scope once and use a distinct hash CTE.
- Do not join all locations before KNN limiting.
- Fetch display metadata only for the bounded result set.
- Use `CAST(:vector AS vector)` or the pgvector-supported parameter binding; do not construct SQL with vector literals by string concatenation.
- Set transaction-local pgvector probes/statement timeout only if benchmarked and compatible with the connection-pool policy.
- Measure exact-vs-IVFFlat recall on a representative fixture or reviewed query sample.

### 14.2 Configurable settings

Add documented defaults only after profiling. The configuration surface should include:

### 14.3 Caching

## 16. Testing and verification plan

### 16.1 Unit tests

Create focused tests for:

- vector normalization and non-finite/zero-vector rejection;

- no-negative equivalence to positive similarity;

- deterministic tie ordering;
- selected-hash exclusion;

### 16.2 Database integration tests

Against a PostgreSQL/pgvector test database, verify:

- extension and approved-model filters work;

- KNN ordering is stable;
- the query plan uses the vector index or an explicitly accepted bounded fallback;

## 17. Acceptance criteria

The beta is ready for controlled archivist testing when:

1. A user can select one to three valid positive file exemplars and remove them.
2. A user can select zero to three valid negative file exemplars and remove them.
3. Invalid, duplicate, overlapping, missing, inaccessible, unembedded, and incompatible examples are rejected safely.
4. A user can choose all, location, project, or CAAN candidate scope using existing semantics.
5. Candidate results are deduplicated by file hash and only come from the authorized selected scope.
6. Selected exemplar hashes never appear in results.
7. Every result has contrastive and ordinary similarity signals, a deterministic rank, a preferred location, and a concise evidence-oriented explanation.
8. Ordinary baseline ordering is viewable without changing the request inputs.
9. Existing `/archives_search`, `/file_search`, `/api/archives_search`, `/api/file_info`, and `/api/project_info` behavior remains unchanged.
10. Telemetry records counts, model/version, beta, scope, timing, candidate/result limits, status, and coverage without storing raw text by default.
11. Search time and query plans meet the benchmarked interactive budget for supported scopes, or the UI clearly handles a controlled timeout/async fallback.
12. Text exemplars are either disabled with an explicit response or use the approved shared provider and exact model contract.
13. Feedback can be recorded without implying that opening a result proves usefulness.
14. Controlled evaluation compares first-useful-result rank, useful top-ten results, result opens/ratings, baseline fallback use, and qualitative failure cases against ordinary similarity.
