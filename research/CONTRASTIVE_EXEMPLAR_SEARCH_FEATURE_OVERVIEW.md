# Contrastive Exemplar Search Feature Specification

## Status

Draft product and technical specification.

This document defines an application-agnostic v1 feature for searching the PPDO Archives by positive and negative semantic examples.

It is intentionally independent of the current Archives App implementation.

It does not authorize a database migration, production deployment, or change to existing default search behavior.

## Purpose

Ordinary semantic similarity retrieves records that are broadly similar to a query file or text prompt.

Within a construction-project archive, ordinary similarity can overvalue shared project context such as building names, project numbers, contractor names, meeting language, and recurring boilerplate.

Contrastive exemplar search lets an archivist describe both the records they want and nearby-but-unwanted material.

The feature should help users find records that are semantically analogous in document purpose, not merely documents from the same project that share common language.

## User Outcome

An archivist should be able to express a request such as:

> Find records like these commissioning and functional-testing documents within Project 4932, but rank down contractor correspondence and project meeting material.

The system should return archive files in a user-selected scope, rank likely analogues above generic project records, and explain the basis for each ranking in plain language.

## V1 Scope

V1 includes the following user capabilities:

- Select one to three existing archive files as positive examples under **Like these**.
- Optionally select zero to three existing archive files as negative examples under **Unlike / ignore these**.
- Optionally provide a short text description as an additional positive or negative example when the application can generate a compatible MiniLM embedding.
- Limit the candidate set to a project, folder, CAAN, or the full accessible archive.
- View ordinary semantic similarity and refined contrastive similarity for every result.
- Open a result using the application's normal file-opening or path-navigation flow.
- Record lightweight usefulness feedback for the result set.

V1 should use only documents with an existing `file_contents.minilm_emb` embedding as semantic examples and candidates.

V1 should not automatically move, file, relabel, delete, or otherwise modify archive records.

V1 should not replace existing filename, path, or full-text search.

V1 should not make contrastive search the application's default search mode.

## Explicit V1 Deferrals

The following capabilities are intentionally deferred unless the application already supports them safely and without new architectural work:

- Uploading a local file solely to use it as an exemplar.
- Persisting an uploaded file after the search completes.
- Bulk selection of large exemplar sets.
- Automatic filing-code recommendations.
- Automatic record classification or relabeling.
- Cross-model comparisons between embeddings generated by different embedding models.
- Chunk-level semantic embedding retrieval.
- Folder-background residualization as a normal user-facing control.

An upload-based exemplar path may be added later if it uses the same trusted extraction, OCR, malware-handling, temporary-storage, and embedding lifecycle as the application already uses for archive ingestion.

## User Interface

The primary feature should appear as an optional search mode named **Find related records**.

The mode should not be described to users as vector arithmetic, subtraction, residualization, or embedding manipulation.

### Positive Examples

The positive-examples area should be labeled **Like these**.

The helper text should say that these examples define the kind of record the user wants to find.

Each selected archive file should appear as a removable chip containing a short filename and enough path or project context to distinguish it from similarly named files.

The file picker should search or browse the archive using existing access-control rules.

The interface should prevent selection of the same file more than once.

### Negative Examples

The negative-examples area should be labeled **Unlike / ignore these**.

The helper text should say that these examples represent material that may be related but should rank lower.

The interface must not imply that the negative examples are literally deleted from the query, the archive, or a document's text.

Negative examples are optional.

The UI should warn gently when users add several unrelated negative examples because an incoherent negative set can make rankings unpredictable.

### Search Scope

The interface should provide the same project, folder, CAAN, and archive-wide scope choices already supported by the application where feasible.

The selected scope determines the candidate set before final results are displayed.

Users must not be able to retrieve candidate records outside their normal archive permissions.

The interface should make the selected scope conspicuous in the result header.

### Results

Every result should display:

- Filename.
- Usable archive path or the application's normal file-location representation.
- Project and filing-code context when available.
- Contrastive similarity score or rank.
- Ordinary similarity score or rank.
- A compact explanation of why the result was promoted or lowered.
- Normal actions for opening, previewing, or navigating to the file.

The contrastive score should be presented as a relative ranking signal, not as a percentage probability that the result is correct.

The result explanation should be evidence-oriented and concise.

Examples include:

- `Matches the commissioning and functional-testing examples.`
- `Ranked lower because it resembles the correspondence examples.`
- `Similar under ordinary search, but mostly because of shared project context.`

### Baseline Comparison

V1 should provide a clear way to compare the refined ranking with ordinary similarity.

An implementation may use a toggle, tabs, a sort option, or a compact side-by-side comparison.

The ordinary ranking is both a useful user fallback and an evaluation baseline.

## Data Model Assumptions

The corpus uses `file_contents.minilm_emb`, a 384-dimensional embedding generated by `all-MiniLM-L6-v2`.

Candidate records are identified by file hash and may have more than one `file_locations` row.

Search results should be deduplicated by file hash before presentation.

The application should choose one or more useful locations to display after ranking distinct files.

Existing filed-record metadata, especially `archived_files.file_code`, `destination_path`, and project context, may be shown as result context but should not be treated as a fully reliable semantic label.

## Ranking Semantics

### Input Vectors

Each selected positive or negative archive file contributes its stored `minilm_emb` vector.

All vectors used together in one search must come from the same embedding model and vector dimension.

The system should normalize each input vector before combining it.

For V1, each selected exemplar should have equal weight.

Future versions may expose or infer weights, but weights should not be a user-facing V1 control.

### Positive Prototype

Let `P` be the normalized embeddings from the positive exemplars.

The positive prototype is the normalized mean of the positive vectors.

```text
positive_prototype = normalize(mean(P))
```

If there are no positive examples, the feature should not run.

### Negative Prototype

Let `N` be the normalized embeddings from the optional negative exemplars.

The negative prototype is the normalized mean of the negative vectors.

```text
negative_prototype = normalize(mean(N))
```

If there are no negative examples, contrastive search is equivalent to positive-exemplar similarity search.

### Contrastive Query

The contrastive query combines desired and undesired semantic directions.

```text
query = normalize(positive_prototype - beta * negative_prototype)
```

`beta` is an application-controlled negative-example strength.

V1 should begin with a conservative fixed value and tune it only with observed result quality.

`beta` should not be exposed as a user control in V1.

The system should reject or safely handle a nearly zero-length combined vector.

This can occur when positive and negative exemplars are nearly identical or unusually contradictory.

### Candidate Ranking

Candidates should initially be retrieved using cosine similarity to the contrastive query and the selected scope.

The primary refined score is:

```text
contrastive_similarity(candidate) = cosine(candidate_embedding, query)
```

The ordinary baseline score is:

```text
ordinary_similarity(candidate) = cosine(candidate_embedding, positive_prototype)
```

Cosine distance in pgvector may be computed with `<=>`.

When vectors are normalized, cosine similarity can be expressed as `1 - cosine_distance`.

The application should exclude every selected exemplar from the result set by file hash.

The application should also exclude exact duplicate hashes represented by those selected exemplars.

### Retrieval and Re-ranking

The application may use the pgvector IVFFlat index to retrieve an initial candidate pool.

If scope filtering, display deduplication, or later experimental scoring makes a single indexed query insufficient, the application may retrieve a bounded candidate pool and re-rank it in application code or SQL.

The implementation must avoid joining every file location before limiting and deduplicating candidate files.

The exact candidate-pool size should be selected from realistic performance testing rather than assumed from the result page size.

## Experimental Folder-Context Discounting

Folder-context discounting is an experimental extension, not a required V1 capability.

It addresses the case where candidate documents appear similar chiefly because they share project-specific language.

### Background Vector

For a selected project or folder `S`, derive a background vector from a representative set of embedded files in that scope.

```text
background = normalize(mean(embedded_files_in_scope))
```

The representative set should exclude the selected positive and negative exemplars.

The implementation should set a minimum sample size and disable the feature when the scope is too small or has insufficient embedding coverage.

### Residualization

For a normalized vector `e` and normalized background vector `b`, calculate a residual vector by removing the component aligned with the background.

```text
residual(e, b) = normalize(e - dot(e, b) * b)
```

For a fair comparison, residualization should normally apply to both the query and every candidate.

```text
score = cosine(residual(query, background), residual(candidate, background))
```

Applying the background adjustment only to the query compares vectors expressed in different semantic frames and should not be the default behavior.

### Limitations

A scope centroid can contain meaningful technical content in addition to generic project context.

Residualization can therefore remove useful signal, especially in semantically narrow projects or folders.

The feature should remain experimental until evaluation shows a consistent gain over ordinary contrastive exemplar ranking.

It should be disabled by default and labeled as an advanced context-discounting experiment if exposed to users.

## Permissions and Data Handling

All archive-file selection, candidate retrieval, result display, preview, and opening actions must honor the application's existing authorization rules.

Exemplar metadata must not reveal the existence or location of inaccessible records.

V1 should retain only the minimum telemetry needed for evaluation.

Selected exemplar identities may be logged only if existing privacy, retention, and operational policies permit it.

Typed text should not be stored beyond the search event unless the user explicitly saves a reusable search recipe and policy permits storage.

The feature must not modify `file_contents.minilm_emb` or any source document.

## Telemetry and Evaluation

The goal of V1 is to determine whether archivists receive more useful results than from ordinary semantic similarity.

Telemetry should record the search mode and ranking behavior without storing more content than needed.

Suggested event fields include:

- Search timestamp and requesting user identifier, subject to existing policy.
- Requested scope type and scope value.
- Number of positive and negative examples.
- Whether a pasted-text example was used.
- Whether ordinary or refined ranking was viewed or selected.
- Whether experimental folder-context discounting was enabled.
- Candidate-pool and displayed-result counts.
- Query duration and final status.
- Result-open, preview, path-copy, or other useful follow-on actions when available.
- Explicit usefulness feedback and optional reason.

The existing `archive_search_runs` telemetry model may be extended or supplemented only after reviewing its current fields and retention intent.

### Evaluation Questions

V1 should be evaluated against ordinary semantic similarity for the same positive examples and scope.

The evaluation should answer:

- Does refined ranking place records that archivists use nearer the top?
- Does it reduce generic correspondence, meeting material, and boilerplate-heavy documents when users provide negative examples?
- Do users understand the distinction between positive and negative examples?
- Do users retain the refined ranking or repeatedly switch back to ordinary similarity?
- Does experimental folder-context discounting improve outcomes enough to justify its complexity?
- Is search performance acceptable for interactive archive work?

Useful measures include result opens, user ratings, first useful result rank, useful results among the first ten, use of the ordinary-ranking fallback, and qualitative review of failed searches.

The system should not infer that a result was useful solely because it was displayed.

## Acceptance Criteria for V1

V1 is ready for controlled user testing when all of the following are true:

- A user can add and remove positive and negative archive-file examples.
- A user can choose a supported search scope.
- The feature returns deduplicated candidate files only from the selected and authorized scope.
- Selected exemplars do not appear in their own results.
- Results show both ordinary and refined similarity information.
- Results provide concise, non-deceptive explanations.
- The user can open or locate a result through the existing application workflow.
- The feature creates enough telemetry to compare refined and ordinary result usefulness.
- Existing search modes continue to function without behavior change.
- The feature performs acceptably on realistic scoped searches.

## Non-Goals

This feature is not a replacement for full-text search.

This feature does not establish ground truth for filing codes or document types.

This feature does not guarantee that semantically high-scoring records are substantively correct, complete, current, or appropriate for a filing decision.

This feature does not use an LLM to summarize, answer questions from, or generate claims about document contents.

This feature does not perform RAG.

## Future Directions

Potential future work includes:

- User-saveable exemplar-search recipes.
- Filing-code prototype and precedent suggestions with human confirmation.
- Project-balanced filing-code centroids.
- Negative examples selected by document type, filing code, or user feedback rather than individual files.
- Chunk-level embeddings for long documents and passage-level explanations.
- Multiple background vectors or principal semantic directions instead of one scope centroid.
- Offline evaluation sets built from reviewed archival decisions.
- Hybrid ranking that combines full-text evidence with exemplar-based semantic ranking.

Any future extension should preserve explainability, user control, ordinary-search fallback, and non-destructive behavior.
